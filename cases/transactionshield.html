Context

Research/portfolio demonstration. Transactions, labels and evaluations are synthetic. It is not a bank system and does not approve or block payments.

02 / The problem

The real challenge behind the screen.

Fraud scoring involves severe class imbalance, leakage risk and precision-recall trade-offs. A model can look impressive on some metrics while producing far too many false review flags to be useful in production.

Project workflow — authored summary
Synthetic records→Chronological split→Model + threshold→FastAPI / SQL→React review console

03 / Process & actions

How the system came together.

01

Generate fictional transactions

Create a reproducible 4,000-record evaluation dataset without personal or cardholder information.

02

Train without leakage

Use train-only fitted preprocessing and chronological train/validation/test splits; compare candidate classifiers.

03

Select and expose caveats

Choose by validation PR-AUC, tune a review threshold using validation F2 and record held-out results without retroactive optimization.

04

Ship a testable application

Implement FastAPI endpoints, database persistence, risk-scoring responses, React dashboards and CSV/history views.

05

Add verification & safeguards

Include API tests, duplicate transaction protection, CI, model artifact integrity checks and operational boundaries.

06 / Key takeaways

What mattered, and what comes next.

  • A fair evaluation should report unfavorable metrics, not only a successful API and UI.
  • Low fraud prevalence makes PR-AUC and precision-recall behavior more useful than accuracy alone.
  • Production gaps include labeled real-world ground truth, calibration, privacy/security reviews, monitoring, and independent validation.
