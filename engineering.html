DECISION 01 · DATA ACCOUNTING

Recognize revenue by transaction state.

Seeded orders→Data quarantine→Completed-line revenue→SQL / Pandas audit→RFM & cohorts

Why the decision matters

Summing all order lines would count cancelled and returned transactions as recognized revenue. The project instead defines a completed-line population and calculates product cost under the same status rules.

Verification already recorded

SQL and Python calculations reconcile within INR 0.01 on the seeded fictional dataset. The README records 72,388 source lines, 100 duplicate identifiers removed, 60 invalid records quarantined and 31,581 completed valid-line orders.

Trade-off / failure to watch

The rule is appropriate to this educational data model, but actual refunds, damaged items and fulfillment terms can complicate accounting. AOV and revenue must refer to the same population.

Next falsification check

Change one status case in a controlled test and confirm both SQL and Pandas update identically. Add a return/partial refund scenario only after defining its accounting treatment.

DECISION 02 · CLASS IMBALANCE

Tell the truth about a weak fraud model.

Synthetic labels→Time split→Validation threshold→Held-out PR-AUC→Review UI

Why the decision matters

At 2.33% positive-class prevalence, accuracy alone would make a mostly negative predictor appear effective. The results report PR-AUC, precision, recall and F1 from an 800-record held-out synthetic set.

Verification already recorded

PR-AUC 0.0319, precision 0.0246, recall 0.1429 and F1 0.0420. A recall-oriented validation F2 threshold of 0.03 generates many false review flags.

Trade-off / failure to watch

Prioritizing recall can increase false positives and operational review costs. These metrics do not justify detecting actual fraud or deploying to a financial institution.

Next falsification check

Re-evaluate on separately sampled, lawful real labels only after data governance, calibration and operational review criteria exist; compare precision at several review-budget thresholds.

DECISION 03 · TIME-SERIES LEAKAGE

Hold out the future, not random rows.

Daily history→Past-only features→Chronological split→Naive benchmark→Forecast

Why the decision matters

Using future sales values in lag or rolling windows can produce misleading performance. DemandPilot creates past-only features and compares LightGBM against a weekly seasonal-naive baseline with chronological train/validation/test boundaries.

Verification already recorded

One-step held-out WAPE: LightGBM 18.469%, seasonal-naive 29.012% on generated sales across eight products and two stores.

Trade-off / failure to watch

The product's recursive forecasts compound error and its displayed intervals are uncalibrated heuristics relying on test residuals. One-step WAPE cannot prove 30-day accuracy or fewer real stockouts.

Next falsification check

Run rolling-origin multi-horizon backtests with a separate calibration slice; evaluate error by SKU/store, promotion and horizon before using reorder suggestions beyond education.

DECISION 04 · RETRIEVAL GROUNDING

Make retrieved evidence inspectable.

Source files→Chunk text→TF-IDF search→Citations→Abstain if unsupported

Why the decision matters

A document answer without a traceable source is hard to audit. EvidenceDesk tests PDF/DOCX/TXT extraction, chunk overlap, citation validity and an offline TF-IDF baseline that does not require an online language model.

Verification already recorded

16 tests passed. The authored retrieval fixture yielded 23 evidence hits from 25 answerable questions and three correct abstentions from five unsupported questions.

Trade-off / failure to watch

Lexical retrieval can miss paraphrases and semantically distant queries. The quoted hit rate is not LLM answer accuracy. Optional MiniLM and Groq inference have not been separately validated in the recorded run.

Next falsification check

Run the negative-question set and add independently authored documents, contradictory passages, OCR failures and semantic retrieval measurements before claiming general question-answering performance.

DECISION 05 · REPORTING SCOPES

Make dashboard metrics explorable, not causal.

Workbook→Data model→KPI measures→Country / city slicers→Insights

Why the decision matters

Distribution by region, cuisine and rating is easier to understand with filterable cards and charts than by reading a spreadsheet row by row. The source README describes the measures and dashboard layout.

Verification already recorded

Dataset summary lists 9,551 restaurants, 250 cuisines, 15 countries, 141 cities and an average rating of 2.89.

Trade-off / failure to watch

These are sample characteristics, not current Zomato business KPIs. Native PBIX/XLSX files are described in the repository material, but an independently verified accessible binary report refresh was not recorded.

Next falsification check

Open the actual workbook/PBIX in Power BI Desktop, confirm filters do not distort distinct counts, and compare country/cuisine KPI totals with the source rows.

REVIEWER CHECKLIST

What I would verify before calling this production-grade.

Data and model proof

  • Independent, permitted real-data evaluation with representative errors
  • Appropriate chronological or genuinely held-out benchmark
  • Disclosed sample size, denominator, confidence and failure cases
  • Repeatable dependency environment and automated tests

Operational proof

  • Documented security and privacy review
  • Production deployment configuration, monitoring and rollback
  • Service-level or business outcome metrics measured on real use
  • Domain-expert review for high-stakes healthcare, finance or safety claims

These are future verification requirements, not completed certifications. The portfolio's own static website QA is a different measurement from ML model or business validation.
